# Internationalization (i18n)

One system, in `src/core/i18n`. English is the source locale; `es-MX` ships
alongside it. Every user-facing string in the product comes from a
dictionary, and the dictionary in use follows the **user**, not the
deployment.

## The active locale

Resolved once per request on the server (`getLocale()` in
`src/core/i18n/server.ts`, React-cached) and applied server-first — the
same rule branding follows, so the first HTML is already in the right
language:

```
signed in:   profiles.locale  →  workspace_settings.default_locale  →  projectConfig.locale
signed out:  workspace_settings.default_locale (public auth-branding RPC)  →  projectConfig.locale
```

Three settings, three owners:

| Level | Where it is set | Who |
| --- | --- | --- |
| Personal (`profiles.locale`) | Account menu → Language | every user, own row only |
| Workspace default (`workspace_settings.default_locale`) | Settings → General → Regional | owner, admin |
| Project default (`projectConfig.locale`) | `src/config/project.ts` | the developer; not editable in the app |

- `profiles.locale` is the user's own choice. `null` means "follow the
  workspace default", which is what a new member gets; picking "Workspace
  default" in the account menu clears it.
- `workspace_settings.default_locale` also drives the pre-auth screens
  (login, verify, expired, invitation) and the invitation email, where no
  user preference exists.
- `projectConfig.locale` seeds new workspaces and is the last fallback.

The root layout renders `<html lang>` from it and mounts `LocaleProvider`;
`AppShell` builds navigation with it. Locale ids are generic BCP 47 tags
(`Locale` in `locales.ts`); nothing in code assumes a particular one.

## Reading copy

| Where | Shell dictionary | Module copy | Dates / numbers |
| --- | --- | --- | --- |
| Client component | `useCopy()` | `useT(moduleCopy)` | `useFormat()` |
| Server component / action | `await getCopy()` | `await getT(moduleCopy)` | `await getFormat()` |

Hooks come from `@/core/i18n/client`, server helpers from
`@/core/i18n/server`, pure pieces (`resolveCopy`, `defineCopy`,
`createFormatters`, `LOCALES`, `isLocale`, `pickLocale`) from `@/core/i18n`.
Nothing imports a fixed locale; a component that renders text takes the
dictionary from the hook or helper, so switching language re-renders it.

## The shell dictionary (`ShellCopy`)

Typed and nested (`copy.ts`, `en.ts`, `es-MX.ts`): chrome, palette,
shortcuts, account menu, the canonical data primitives, form defaults,
error/404 states, the auth surface, roles, the overview landing, audit
summaries, and the core emails. Interpolated strings are functions so each
locale controls word order. `nav.modules` holds every module's on-screen
name, description, and child labels — the registry carries identifiers
only, and `buildNavigation()` resolves names at build time.

The i18n test enforces key parity between `en` and `es-MX` (same shape,
same types) and that every registry module with navigation has a name in
every locale.

## Module copy: the `copy.ts` convention

A module ships its own dictionary in `src/modules/<id>/copy.ts`:

```ts
import { defineCopy } from "../../core/i18n/t.ts"

export const settingsCopy = defineCopy({
  en: { "settings.team.invite": "Invite member", "settings.team.summary.members.one": "{n} member", "settings.team.summary.members.other": "{n} members" },
  "es-MX": { "settings.team.invite": "Invitar miembro", "settings.team.summary.members.one": "{n} miembro", "settings.team.summary.members.other": "{n} miembros" },
})
```

- Keys are English dotted identifiers prefixed with the module id
  (`settings.team.invite`); values are the locale's sentences. English is
  the source and the fallback for any locale that lacks a key.
- `{name}` placeholders interpolate: `t("settings.team.dialog.sent", { email })`.
- Plurals are two keys, `<key>.one` / `<key>.other`, read with
  `t.n("settings.team.summary.members", n)` (`{n}` is set for you).
- A missing key renders as the key itself and warns once outside
  production, so typos are visible in development and never blank in
  production.
- Components: `const t = useT(settingsCopy)`; server actions:
  `const t = await getT(settingsCopy)`. Module-level constants that need
  copy become functions of `t`.
- Server actions return already-localized messages, so the client shows
  them as they are.

Add a parity test to the module (see `translator.test.ts`): every English
key has a counterpart in every shipped locale, and vice versa.

## Dates and numbers

`createFormatters(locale, timeZone?)` (`format.ts`) is the only place
`Intl` is configured: `date`, `dateTime`, `time`, `number`, `daysBetween`.
`useFormat()` / `getFormat()` default the zone to the workspace's
`time_zone` (Settings → General; `projectConfig.timeZone` before sign-in),
so "today" and period boundaries agree across shell and modules wherever
a user signs in from. Components never call `toLocaleString` themselves. `pageSummary()` in
`src/core/data/query.ts` takes the copy strings and number formatter from
the caller for the same reason.

## Adding a locale

1. Add the tag to `LOCALES` and its name to `LOCALE_NAMES` (`locales.ts`).
2. Add `src/core/i18n/<tag>.ts` satisfying `ShellCopy`, register it in
   `index.ts`.
3. Add the tag's dictionary to every module's `copy.ts` (or accept the
   English fallback for that module).
4. Run `pnpm test` — parity tests fail on anything missing.

No migration is needed: the database checks only the tag's shape.

## What is NOT localized

Identifiers in code and the database (roles, action names, module ids,
column keys) stay English; render them through the dictionary
(`copy.roles.labels`, `copy.nav.modules`). Supabase's own auth emails come
from `supabase/config.toml` templates, not from this system.
